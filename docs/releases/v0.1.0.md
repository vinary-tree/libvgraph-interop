# Version 0.1.0 release candidate

Version 0.1.0 is the candidate for the first immutable release of the narrow snapshot boundary
between domain adapters and `libvgraph`. This record identifies the compatibility contract,
formal provenance, required acceptance evidence, and publication procedure. It becomes a release
record only when the workflow described in the [immutable release process](process.md) publishes
the signed tag.

## Candidate contract

The release owns exactly one representation: schema `LVGI-CSR-FWD-V1!`, version 1.0, with an
80-byte little-endian header and canonical forward compressed sparse row (CSR) payload. It exposes
opaque 32-byte semantic-profile identities, domain-separated BLAKE3 digests, checked resource
limits, deterministic structural-work admission, and cooperative cancellation. It does not own
stable labels, reverse adjacency, graph algorithms, domain payloads, provenance, transport, or
authentication.

The release depends on exact versions `libvgraph` 0.1.0 and BLAKE3 1.8.7. Its minimum supported
Rust version is 1.85. Persisted version-1 bytes and digest construction are normative; incompatible
changes require a new schema identity and an explicit decode-validate-re-encode migration.

## Formal provenance

Production behavior refines immutable `vinary-tree/libvgraph` commit
[`83e1cdd489369dcd7d53fb8fdf6041ef3f5cb697`](https://github.com/vinary-tree/libvgraph/commit/83e1cdd489369dcd7d53fb8fdf6041ef3f5cb697).
The candidate archive contains exact hashes for 27 formal artifacts and a 75-row mapping from
proved invariants to production symbols and acceptance tests. The bundled provenance scripts read
the immutable commit object and reject a missing, changed, reordered, duplicated, substituted,
additional, or unmapped artifact.

## Acceptance evidence

Publication requires the final clean candidate commit to pass:

- Rocq, TLC, TLA+ causal-mutant, Z3, Verus, and independent-oracle gates recorded in the
  [formal provenance](../../formal/README.md);
- current-Rust and Rust 1.85 formatting, compilation, strict Clippy, unit, contract, property,
  exhaustive, golden-vector, malformed-input, stack-safety, doctest, and rustdoc gates;
- all 531 directed graphs through three vertices, 1,593 profile encodings, 9,321 lawful dense
  renamings, and 180,696 strict-prefix rejection cases;
- a 100,000-input arbitrary-byte fuzz campaign with no crash, timeout, or out-of-memory failure;
- every generated source mutant with zero survivors and zero timeouts;
- the complete 100,000-vertex lifecycle on a 64 KiB native thread stack;
- dependency advisory, license, duplication, wildcard, and source-policy gates;
- reproducible PlantUML rendering and read-only vinary-doc-lint validation; and
- exact publish-archive inventory and checksum validation.

The [verification method](../science/verification.md) defines what each result establishes and
where continuous integration retains the raw evidence.

## Publication and authenticity

The final source commit and annotated `v0.1.0` tag must be SSH-signed. The GitHub release workflow
verifies the tag against the protected repository allowlist before candidate execution, proves
identity with protected `main`, runs every release gate on Rust 1.85, creates a draft, verifies the
crates.io checksum, generates build-provenance and SBOM attestations, reconciles four exact assets,
and publishes only after GitHub confirms release immutability is enabled.

Because a trusted publisher can be configured only after crates.io has allocated the crate name,
version 0.1.0 uses the registry's bootstrap sequence: publish the exact verified tag archive with
an ephemeral least-privilege token, remove that token immediately, then configure
`vinary-tree/libvgraph-interop`, workflow `release.yml`, and environment `crates-io` as the trusted
publisher. Every subsequent release uses only the repository's OpenID Connect workflow.

## Upgrade and rollback

No earlier published version exists. After publication, consumers should pin 0.1.0 when persisted
bytes cross a trust boundary, retain the authenticated expected digest with the bytes, and
configure finite admission limits. Rollback means selecting an earlier application artifact while
continuing to decode only the exact schemas that artifact advertises; a deployment must never
reinterpret version-1 bytes or replace a published archive.
